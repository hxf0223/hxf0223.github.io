# 中文技术笔记润色（去 AI 味）

把笔记正文改得**通顺、不啰嗦、符合逻辑**，像作者本人在更清楚地说话。一条铁律贯穿始终：**只改表达，不改信息**——不新增事实，不删除主张，不改变判断的强度、范围和确定程度。

这不是敏感词替换器。看到「赋能」「标志着」不是机械换个词，而是问：这句拿掉套话之后，真正想说的具体内容是什么？写不出具体内容的句子，多半该删，不该改。

## 适用与不适用的文本

本 skill 为本仓库的简体中文技术笔记定制（C++、Linux、处理器/内存架构、性能优化、编程工具、环境搭建、行业观察）。

- 技术说明、操作步骤、配置记录：以准确、克制为先，清理翻译腔和空话即可，不注入个性，不把笔记改成博客腔。
- 行业笔记、观点、随笔：允许保留作者的犹豫、偏好和插话，清理模板腔后允许有个人判断的语气。
- 纯代码、命令、报错信息不在范围内；代码注释只在用户明确要求时才改。

## 保护清单（动笔前先圈出，全程原封不动）

1. YAML front matter（`---` 之间的一切：`title`、`date`、`categories`、`tags`、`toc` 等）。
2. 代码块（``` 围栏内）、行内代码、命令、路径、环境变量。
3. 链接地址与链接文字、图片引用。
4. Jekyll/Liquid 标签、math 公式、mermaid 代码。
5. 直接引语、参考资料列表、专有名词与品牌官方大小写（GitHub、LLVM、GDB）。
6. 简体中文不转繁体，不把大陆用语替换成台湾用语（「视频→影片」这类替换规则禁止使用）。
7. 术语不强改：`token`、`API`、`cache` 等保持原文写法；只有同一对象前后叫法不一致时才统一，并沿用作者已有的叫法。

## 工作流程

1. **判断任务类型**：轻度润色（清理措辞和标点）、深度改写（重排句子、合并弱句、调整段落）、只诊断不改。
2. **通读并标记**：读全文一遍，按 [references/patterns.md](references/patterns.md) 标记问题，最重的先处理。段落形状和句子同样要看：跨两句的对照、连续三段同一收尾，是同一个问题在更大尺度上的表现。
3. **建信息账本**：记录原文的事实、数字、命令、结论、否定和不确定程度。改写时可以重组、合并、删冗余，但账本上每项实质信息都要在改写版里找得到。
4. **改写**，按这个顺序动手：
   - 先删：对话残留、免责声明、口号式收尾、预告式导言——删掉不用补。
   - 再具体化：夸大的意义、空泛的判断，改回具体事实或明确结论；写不出具体内容就删。
   - 再降格式：滥用破折号、机械加粗、为凑数而排比，降回正常密度。
   - 最后调结构：段落顺序、开头结尾、跑题段（见下文「C 符合逻辑」）。
   - 禁止换汤不换药：删「标志着」不能补「象征着」，删「赋能」不能补「助力」。
5. **保真回读**：对照信息账本逐项核对——有没有新增事实？有没有丢主张？有没有把「可能」改成「会」、把疑问改成断言？然后朗读一遍，还有哪里不像作者本人写的。

长文（约 1500 字以上）防缩水：改动尽量逐句对应原文，不要把几句合并成一处导致无法对照；承担节奏的转场句不建议删。篇幅变短是正常的，但每个实质信息点必须保留。

## 三大目标的核心规则

### A 通顺：消除翻译腔和欧化句式

- 拆开英文句法硬套中文的句子；少用「对于……来说」「基于……」「使得……得以……」「围绕着……展开」。
- 每句有明确的主语和动作，少写无主句串联；被动句只有主动表达更清楚时才改。
- 长短句自然交替，不把每句写成同样长度；同一对象不要轮换称呼（主人公/主要角色/核心人物），重复最清楚的那个叫法。
- 「它、这、其、该」开头的句子过密时，指代清楚的前提下省略或合并。

### B 不啰嗦：提高信息密度

- 删没有机制解释的大词：「颠覆」「革命性」「重大突破」「深刻改变」。判断要落地到具体动作、约束、成本或结果。
- 删填充短语：「在这个时间点」→「现在」，「由于……这一事实」→「因为……」，「具有……的能力」→「能……」。
- 删「从而、进而、确保、彰显」式句尾包装：原文没有因果证据就不要补因果。
- 「不是 A 而是 B」整篇最多一次，其余直接说 B；「不仅仅……更是……」同族处理。
- 三连排比里只有两个真观点时，删凑数的那个；确有三项事实时照实保留。
- 过度限定收紧到与证据相符：「可能在某种程度上或许会产生一些影响」→「可能会影响」；但不能把「可能」擅自改成「会」。

### C 符合逻辑：文章级结构

- 开头尽快立题：第一段要提出本文真正处理的问题；「在当今……时代」「随着……的发展」这类时代帽子直接删，第一句就该有只有这篇笔记才有的信息。
- 每个段落有一个功能：交代背景、给出结论、展开论据、举例、转折、收束。既不推进主线也不提供必要信息的段落，删、并、挪，不硬留。
- 结尾回应开头提出的问题，落在最后一个具体事实上；「未来可期」「让我们拭目以待」这类罐头结尾删掉后不必补新的，停在未解的具体问题上也可以。
- 不强行凑三段论和「首先/其次/最后」：结构服从逻辑，不服从对称。硬凑的那一点删掉，过渡词多半可以直接拿掉。
- 「各有优缺点」「取决于多方面因素」代表整段没有判断：改成作者的实际选择和理由；作者没给就标注「（需作者补充）」，不代编。
- 「这意味着……」先问：谁在推论、根据什么。三个都答不出来就删。

### D 标点与排版

- 全文标点风格与原文保持一致、全篇统一；同一篇里不要混用 `""` 和 `「」`。
- 中文破折号不一刀切禁用，但短段内反复用 `——` 制造揭示感时，改成逗号、句号、冒号或括号。
- 不密集使用冒号，尤其避免连续多句都靠冒号展开。
- 列表和加粗为内容服务时保留；把普通段落切成「**加粗小标题**：解释」的模板卡片时，合并回自然段。
- 标题后紧跟一句复述标题的暖场句（「性能很重要」），删掉暖场句，让标题直接连接具体内容。

## 误判保护

单一现象不可靠，只在多个模式共同出现并损害表达时修改：一个「此外」、一个破折号、三项真实清单、中文引号、正式词汇、语法完美，单独出现都不是证据。引语、代码、讲解某个套话时例子里的套话是内容，不是清理对象。

保留这些真人痕迹，不要磨平：具体反常的细节、保留意见和未解决的张力、作者能解释其用意的重复与插话、方言和口头禅。技术文里必要的路标（步骤编号、警告、注意事项）不属于 AI 腔。

不代作者生产内容：具体例子、个人经历、立场转折，作者没写的就标注「（需作者补充）」占位，不编造。编造的「我以前理解错了」比空话糟糕得多——空话只是无聊，假故事是说谎。

## 输出模式

- **文件模式（默认）**：用户指向具体文件时，只改正文，保护清单内容不动，文件里只留终稿；对话中给一份简短改动摘要（改了什么、为什么，3–6 条）。动笔前用 `git diff` 确认文件当前状态，避免覆盖用户别处的修改。
- **只诊断模式**：用户说「先标问题不要改」「帮我看看哪里有问题」时，只列问题清单（位置、原句、问题类型、建议），不给完整改写版。
- **重大重构**：需要重排全文结构、删除成段内容时，先在对话里列出调整方案等用户确认，再动文件。
- 改动摘要里可以给 1–2 个前后对照例句；除非用户要求，不展示逐句清单和评分。
