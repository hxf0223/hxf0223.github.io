## 1. 概述与背景

大模型的上下文窗口越长，越容易出现推理延迟高、上下文漂移和无序遗忘：跨会话的用户偏好、代码重构的决策链这些状态，纯 RAG 的无状态向量检索维护不了。2026 年腾讯开源的 Hy-Memory 2.0（混元认知记忆框架）把记忆做成了一等公民，除对话记忆（Chat Memory）外还提供了面向工程场景的编程记忆（Coding Memory）。

本文记录我们在局域网异构集群上的实际部署与接入过程，回答五个问题：

1. Hy-Memory 2.0 的核心架构与 L0-L7 记忆分层是什么；
2. 它以常驻服务还是 Hook/MCP 方式运行；
3. 专用抽取模型 `Hy-Memory-30B-A3B` 是否必须部署；
4. 在 Ubuntu 26.04 上如何做生产级部署（uv 虚拟环境、本地嵌入服务、Systemd 守护）；
5. 五个主力 Agent（agy、codex、zcode、prime-agent、pi）如何接入。

## 2. 核心架构速览

### 2.1 双进程认知模型

Hy-Memory 2.0 借鉴 System 1 / System 2 双系统理论，构成「反应式工作记忆 + 深层陈述记忆」的闭环：

```text
     Agent 交互触发
           │
           ▼
┌──────────────────────┐        即时感知         ┌──────────────────────┐
│  System 1: 工作记忆  │ ─────────────────────► │  上下文精准注水装配  │
│  (Working Memory)    │ ◄───────────────────── │  (In-context Prompt) │
└──────────────────────┘        命中注入         └──────────────────────┘
           │
           │ (异步入库 / 周期性触发)
           ▼
┌────────────────────────────────────────────────────────────────────┐
│  System 2: 深度反思与记忆整合 (Reflective Consolidation)           │
│  • 原子事实提取 (Atomic Fact Extraction)                           │
│  • 矛盾检测与版本演进 (Conflict Resolution & Time Decay)           │
│  • 拓扑图谱归纳 (Graph Induction)                                  │
└────────────────────────────────────────────────────────────────────┘
           │
           ▼
┌────────────────────────────────────────────────────────────────────┐
│  混合存储底座                                                      │
│  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐  │
│  │   SQLite         │  │   ChromaDB       │  │   Kuzu Graph DB  │  │
│  │  (元数据/状态机) │  │ (Dense语义向量库)│  │ (属性知识图谱)   │  │
│  └──────────────────┘  └──────────────────┘  └──────────────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

- **System 1（快速通道）**：维护当前会话或 Coding 任务的即时状态、短期焦点与符号快照，毫秒级响应；
- **System 2（深度通道）**：后台异步执行，用 LLM 对交互切片做原子分解、时间衰减修正、实体消歧与多版本偏好合并，防止知识膨胀。

我们实测的数据落盘与上图一一对应：`~/.hy_memory/data/` 下 `cache.db`/`history.db`（SQLite 状态与流式日志）、`vector_db/`（Chroma 向量库），Kuzu（venv 内装的是 0.11.3）按需为图谱层提供存储。

### 2.2 记忆分层（L0–L7）

| 层级   | 概念定义                      | 存储形态                | 应用场景                         |
| :----- | :---------------------------- | :---------------------- | :------------------------------- |
| **L0** | Raw Messages / Turn Slices    | 关系型流式追加日志      | 会话原始回溯、审计与回滚         |
| **L1** | Atomic Facts & Event Facts    | 三元组与键值事实        | 用户习惯、环境常量、硬约束记录   |
| **L2** | Session Summaries             | 周期性语义摘要块        | 跨轮次宏观背景铺垫               |
| **L3** | Contextual Clusters           | 局部 Dense 向量聚类     | 相似上下文的主动语义召回         |
| **L4** | Entity-Relation Graph         | 实体-谓词-实体 知识网络 | 复杂实体级连依赖查询（GraphRAG） |
| **L5** | Cognitive Schemas             | 规则、思维链模版与模式  | 沉淀专家行为策略与习惯模板       |
| **L6** | Domain Mental Models          | 领域特定心智概念库      | 业务体系深度共识与业务规则映射   |
| **L7** | Long-term Intention & Persona | 用户持续演化的意图画像  | 驱动高阶个性化自主决策           |

实测中 `/api/v1/add` 写入的记忆经 LLM 抽取后以 `l2_fact` 等层级标记存入 `list` 结果，与分层设计吻合。

### 2.3 编程记忆（Coding Memory）

针对代码工程场景，文本摘要容易丢语法结构与文件依赖，Hy-Memory 2.0 单独设计了 Coding Memory：

- **Working Memory**：当前工作区的任务目标、未完成 TODO、活跃修改文件集与编译失败上下文；
- **Experience Memory**：历史踩坑经验（Bug Fix Patches）、高难度重构模式与项目专属规范；
- **Diff Evolution Chain**：追踪 Git Commit / Patch 变迁背后的意图与因果链，回答「这段代码为什么必须这样写」。

## 3. 两个关键选型问题

### 问题 1：常驻服务，还是 Hook/MCP 调用？

**答案是「常驻守护服务 + 轻量无状态胶水层」的组合，两侧各司其职。**

内核必须常驻（我们直接用官方自带的 HTTP 服务 `python -m hy_memory.server`，监听 `0.0.0.0:19527`），原因有三：

1. **嵌入式数据库的单进程写锁**。底层 SQLite / ChromaDB / Kuzu 都是文件级独占锁。如果各 Agent 各自用 Python SDK 打开同一份数据目录，并发读写立刻触发 `sqlite3.OperationalError: database is locked` 或 Kuzu 进程锁崩溃。必须由单一守护进程串行化所有读写。
2. **索引常驻的开销**。向量索引、图拓扑加载进内存后，API 响应在毫秒级；若每次提问都冷启动 Python 进程加载库文件，延迟无法接受。
3. **多设备共享**。19527 绑定 `0.0.0.0`，局域网内的 136、240 乃至 Windows 客户端共用一个全局记忆库。

Agent 侧则保持极轻：一个**零依赖的 MCP stdio 桥接脚本**（仅用 Python 标准库 `urllib` + `json`）把请求转发给 19527；或干脆用 Skill 直接 `curl` HTTP API。Agent 端不装任何重型库。

### 问题 2：`Hy-Memory-30B-A3B` 是必需的吗？

**不是必需，可由任意 OpenAI 兼容的通用 LLM 平替。**

- 该模型是 MoE 架构，总参 30B、单次激活约 3B，针对记忆提取任务做过归因强化学习微调，长对话的结构化事实抽取和时序修正更稳；
- 但它对外就是标准 OpenAI Chat Completions 协议，没有任何私有格式。

我们把 `MEMORY_LLM_BASE_URL` 指向 DeepSeek 官方 API（`deepseek-chat`），实测记忆抽取、`Memory: ...` 格式化输出、标签归类全部正常；同理也可以指向 240 Jetson 上的 `qwen3.8-27b`（本机 8787 的 headroom 压缩代理上游就是它），不必为 Hy-Memory 单独腾显存。

### 4.3 嵌入服务 `embed_server.py`

用 fastembed 起一个 OpenAI 兼容的 `/v1/embeddings` 微服务，只绑定本机回环（19527 的记忆内核是唯一客户端）。真实文件 `~/hy_memory_service/embed_server.py`：

```python
# -*- coding: utf-8 -*-
import os
os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"
from fastapi import FastAPI, Request
from fastembed import TextEmbedding
import uvicorn

app = FastAPI(title="Hy-Memory Local Embedding Server")
embed_model = TextEmbedding("BAAI/bge-small-zh-v1.5")

@app.get("/healthz")
async def healthz():
    return {"status": "ok"}

@app.post("/v1/embeddings")
async def embeddings(req: Request):
    body = await req.json()
    inp = body.get("input", "")
    if isinstance(inp, str):
        inp = [inp]
    vectors = [v.tolist() for v in embed_model.embed(inp)]
    return {
        "object": "list",
        "data": [{"object": "embedding", "embedding": v, "index": i} for i, v in enumerate(vectors)],
        "model": "bge-small-zh-v1.5",
        "usage": {"prompt_tokens": 0, "total_tokens": 0}
    }

if __name__ == "__main__":
    uvicorn.run(app, host="127.0.0.1", port=8089, log_level="warning")
```

## 5. 接入层：零依赖 MCP 桥接与全局 CLI

Windows 端装 Kuzu 要 MSVC 编译、Python 3.14 没有预编译 wheel，所以接入层的设计原则是：**客户端机器零第三方依赖**，一个纯标准库脚本走 stdio JSON-RPC，把请求转发给 19527。

### 5.1 MCP 桥接 `hy_mcp_server.py`

Linux 上放在 `~/hy_memory_service/hy_mcp_server.py`，Windows 上放 `E:\work\ai\hy_mcp_server.py`。行为由三个环境变量控制：`HY_MEMORY_HOST`（默认 `127.0.0.1`）、`HY_MEMORY_PORT`（默认 `19527`）、`HY_MEMORY_USER`（默认 `default_user`）。**非本机运行时必须显式设 `HY_MEMORY_HOST=192.168.137.136`。**

```python
def _http_request(endpoint: str, data: dict = None, method: str = "POST"):
    url = f"{BASE_URL}{endpoint}"
    headers = {"Content-Type": "application/json; charset=utf-8"}
    body = json.dumps(data, ensure_ascii=False).encode("utf-8") if data is not None else None

            raw = resp.read().decode("utf-8", errors="ignore")
            return json.loads(raw) if raw else {}
    except urllib.error.URLError as e:
        return {"error": f"Hy-Memory 服务通信失败 ({url}): {e}"}
    except Exception as e:
        return {"error": f"请求异常: {e}"}

def handle_search(arguments: dict):
    query = arguments.get("query", "")
    limit = int(arguments.get("limit", 5))
    scene = arguments.get("scene", "chat")
    payload = {
        "query": query,
        "user_ids": [DEFAULT_USER],
        "limit": limit,
        "scene": scene,
        "min_score": 0.2
    }
    res = _http_request("/api/v1/search", payload)
    if "error" in res:
        return f"检索失败: {res['error']}"

    memories = res.get("memories", {})
    normal = memories.get("normal", [])
    schema = memories.get("schema", [])
    facts = res.get("facts", [])
    exps = res.get("experiences", [])

    results = []
    if normal:
        results.append("【相关记忆】:")
        for m in normal:
            results.append(f"- [{m.get('score', 0):.2f}] {m.get('content')}")
    if schema:
        results.append("【心智模式/图式】:")
        for s in schema:
            results.append(f"- {s.get('content')}")
    if facts:
        results.append("【事实层】:")
        for f in facts:
            results.append(f"- {f.get('content', f)}")
    if exps:
        results.append("【经验层】:")
        for e in exps:
            results.append(f"- {e.get('content', e)}")

    if not results:
        # 尝试查询是否有 L0 用户画像或最新记忆
        prof = _http_request("/api/v1/user_profile", {"user_id": DEFAULT_USER})
        if prof.get("profile") and prof["profile"].get("content"):
            return f"未直接命中语义记忆，当前用户画像：{prof['profile'].get('content')}"
        return "未检索到相关的长期记忆记录。"
    return "\n".join(results)

def handle_add(arguments: dict):
    content = arguments.get("content", "")
    scene = arguments.get("scene", "chat")
    payload = {
        "data": content,
        "text": content,
        "user_id": DEFAULT_USER,
        "scene": scene
    }
    res = _http_request("/api/v1/add", payload)
    if "error" in res:
        return f"记忆写入失败: {res['error']}"
    if res.get("success"):
        return f"记忆已成功写入 Hy-Memory (id: {res.get('memory_id')}, scene: {res.get('scene')})"
    return f"记忆写入返回: {json.dumps(res, ensure_ascii=False)}"

def handle_profile(arguments: dict):
    user_id = arguments.get("user_id") or DEFAULT_USER
    payload = {"user_id": user_id}
    res = _http_request("/api/v1/user_profile", payload)
    if "error" in res:
        return f"获取画像失败: {res['error']}"
    profile = res.get("profile", {})
    return json.dumps(profile, ensure_ascii=False, indent=2)

def handle_list(arguments: dict):
    limit = int(arguments.get("limit", 10))
    payload = {"user_id": DEFAULT_USER, "limit": limit}
    res = _http_request("/api/v1/list", payload)
    if "error" in res:
        return f"列出记忆失败: {res['error']}"
    # 注意：/api/v1/list 的返回嵌套在 "vdb" 键下（2026-10-19 修复的解析 bug）
    memories = (res.get("vdb") or {}).get("memories") or res.get("memories") or []
    if not memories:
        return "当前暂无记忆记录。"
    lines = [f"共 {len(memories)} 条记忆:"]
    for m in memories:
        lines.append(f"- [{m.get('layer', 'info')}] {m.get('content', '')}")
    return "\n".join(lines)

def dispatch_tool(name: str, arguments: dict):
    if name == "hy_memory_search":
        return handle_search(arguments)
    elif name == "hy_memory_add":
        return handle_add(arguments)
    elif name == "hy_memory_user_profile":
        return handle_profile(arguments)
    elif name == "hy_memory_list":
        return handle_list(arguments)
    return f"未知工具: {name}"

def main():
    while True:
        line = sys.stdin.readline()
        if not line:
            break
        line = line.strip()
        if not line:
            continue
        try:
            req = json.loads(line)
        except Exception:
            continue

        req_id = req.get("id")
        method = req.get("method")

        if method == "initialize":
            resp = {
                "jsonrpc": "2.0",
                "id": req_id,
                "result": {
                    "protocolVersion": "2024-11-05",
                    "capabilities": {
                        "tools": {}
                    },
                    "serverInfo": {
                        "name": "hy-memory-mcp",
                        "version": "2.0.3"
                    }
                }
            }
            sys.stdout.write(json.dumps(resp, ensure_ascii=False) + "\n")
            sys.stdout.flush()
        elif method == "notifications/initialized":
            pass
        elif method == "tools/list":
            resp = {
                "jsonrpc": "2.0",
                "id": req_id,
                "result": {
                    "tools": TOOLS
                }
            }
            sys.stdout.write(json.dumps(resp, ensure_ascii=False) + "\n")
            sys.stdout.flush()
        elif method == "tools/call":
            params = req.get("params", {})
            tool_name = params.get("name")
            arguments = params.get("arguments", {})
            try:
                text_out = dispatch_tool(tool_name, arguments)
                resp = {
                    "jsonrpc": "2.0",
                    "id": req_id,
                    "result": {
                        "content": [
                            {
                                "type": "text",
                                "text": str(text_out)
                            }
                        ],
                        "isError": False
                    }
                }
            except Exception as e:
                resp = {
                    "jsonrpc": "2.0",
                    "id": req_id,
                    "result": {
                        "content": [
                            {"type": "text", "text": f"Error executing {tool_name}: {e}"}
                        ],
                        "isError": True
                    }
                }
            sys.stdout.write(json.dumps(resp, ensure_ascii=False) + "\n")
            sys.stdout.flush()
        elif method == "ping":
            resp = {"jsonrpc": "2.0", "id": req_id, "result": {}}
            sys.stdout.write(json.dumps(resp, ensure_ascii=False) + "\n")
            sys.stdout.flush()
        else:
            if req_id is not None:
                resp = {
                    "jsonrpc": "2.0",
                    "id": req_id,
                    "error": {
                        "code": -32601,
                        "message": f"Method not found: {method}"
                    }
                }
                sys.stdout.write(json.dumps(resp, ensure_ascii=False) + "\n")
                sys.stdout.flush()

if __name__ == "__main__":
    main()
```

## 6. 全链路数据流：两个脚本各自给谁用

整套部署里我们只自写了两个脚本，它们分处链路两端、服务对象完全不同：

```text
codex / zcode / prime / agy                  pi / 人工排障
           │ MCP (stdio)                           │ shell
           ▼                                       ▼
hy_mcp_server.py（MCP 桥接）                  ~/.local/bin/hy-memory（CLI）
           │                                       │
           └─────────── HTTP /api/v1/* ────────────┘
                               │
                               ▼
         hy_memory.server :19527  （记忆内核 · 官方包）
                      │                      │
                      │ 写入/检索时向量化    │ LLM 抽取（System 2）
                      ▼                      ▼
         embed_server.py :8089     DeepSeek API（可换 240 的 qwen）
     （本地 BGE 嵌入，仅内核使用）
```

**`embed_server.py`——给记忆内核自己用的"向量化工人"。** Hy-Memory 在 pro 模式下，每次写入和语义检索都要先把文本变成 512 维向量才能进 Chroma 向量库，而它的嵌入器设计成外接的 OpenAI 兼容接口（`.env` 里的 `MEMORY_EMBEDDER_BASE_URL`）。这个接口要么用云端 embedding API（花钱、数据出内网），要么本地起一个——`embed_server.py` 就是本地实现：fastembed 加载 `bge-small-zh-v1.5`（约 100MB，CPU 毫秒级，中文效果好），在 8089 上暴露 `/v1/embeddings`。**它唯一的客户端就是 19527 上的记忆内核**，这也是它只绑 `127.0.0.1` 的原因——没有任何 Agent 直连 8089。独立成进程的好处是可以独立重启：xet 事故（§8.2）里坏的只是嵌入服务，记忆内核全程存活；代价是它挂掉时全链路静默失效，排障口诀见 §8.2 结尾的教训。

**`hy_mcp_server.py`——给各 Agent 用的"翻译官"。** Agent 侧说 MCP（stdio JSON-RPC 子进程），hy-memory 侧说 HTTP REST，两头语言不通；又不能让 Agent 直接打开数据库文件（SQLite/Chroma/Kuzu 是单进程写锁，必须全走 19527 串行化），也不该让客户端机器为此装 chromadb/kuzu 这套重型依赖——Windows 上 kuzu 还要 MSVC 编译。所以桥接只用 Python 标准库，任何有 python3 的机器拷一个文件即可接入，`HY_MEMORY_HOST/PORT/USER` 三个环境变量决定连到哪台、以谁的身份写（§7）。它的用户是 codex、zcode、prime-agent、agy 四家（各自的会话 spawn 一个进程）；pi 不走它，用 §5.2 的 CLI。

一句话总结：`embed_server.py` 负责"内核 ↔ 向量"，`hy_mcp_server.py` 负责"Agent ↔ 内核"；两个脚本的共同原则是——重依赖与数据文件只留在 136 的守护进程里，客户端永远只需要标准库。

### 8.1 常规验证命令集

### 8.2 事故实录：嵌入服务崩溃循环（xet 401）

**症状**（2026-10-19 上午发现）：`hy-embed.service` 重启计数飙到 661+，8089 端口无监听；`/api/v1/add` 返回 HTTP 200 但 `success: false, error_message: "Connection error."`；更隐蔽的是 **`/api/v1/search` 不报错、只返回空结果**——所有 Agent 的记忆写入与检索静默失效。

**根因**：fastembed 下载 `bge-small-zh-v1.5` 走 huggingface_hub 的 xet 后端，直连 `cas-server.xethub.hf.co` 被 401 拒绝。`HF_ENDPOINT=https://hf-mirror.com` 只改普通 HTTP 下载路径，hf-mirror 不代理 xet CDN，于是每次冷缓存都崩溃。

**修复**（已固化）：

```bash
# .env 中加入（systemd 的 EnvironmentFile 会自动带上）
HF_HUB_DISABLE_XET=1

# 预热模型缓存（此后服务即使重启也直接命中缓存，14 秒完成下载验证）
cd ~/hy_memory_service && HF_ENDPOINT=https://hf-mirror.com HF_HUB_DISABLE_XET=1 \
  .venv/bin/python -c "from fastembed import TextEmbedding; print(len(list(TextEmbedding('BAAI/bge-small-zh-v1.5').embed(['测试']))[0]))"
```

修复后 `hy-embed` 自愈（`Restart=always` 下一轮重启即成功），add/search 全链路恢复。

**教训**：嵌入链路是这套系统最脆的一环，且它的故障是静默的——排障先打两个 `/healthz`，写操作永远检查 `success` 字段而不是 HTTP 状态码。

### 8.3 同日修复的接入层 bug

| 位置                           | 问题                                                                                             | 修复                                      |
| :----------------------------- | :----------------------------------------------------------------------------------------------- | :---------------------------------------- |
| `hy_mcp_server.py` `list`      | `/api/v1/list` 返回 `{"vdb":{"memories":[...]}}`，脚本按顶层 `memories` 解析，永远显示"暂无记忆" | 改为取 `res["vdb"]["memories"]`（带回退） |
| `~/.local/bin/hy-memory` `add` | 不检查 `success` 字段，失败也打印"写入成功"（假成功误导 Agent）                                  | `success` 为假时报错并退出码 1            |
| agy / prime 的 MCP 注册        | 缺 `HY_MEMORY_USER` env，记忆写到 `default_user`，与 codex/zcode 视图分裂                        | 补齐 env 三件套，统一 `hxf0223`           |

### 8.4 常见问题清单

1. **`sqlite3.OperationalError: database is locked`**
   多个客户端直接打开了同一份本地 SQLite/ChromaDB 文件。禁止 Agent 侧直连数据目录，一切读写走 `19527` 守护进程（这正是 §3 问题 1 采用中心服务的原因）。
2. **Kuzu 在 Windows 下编译报错（cl.exe 缺失 / GBK 编码 / Python 3.14 无 wheel）**
   不要在 Windows 装 Kuzu。用 §5 的零依赖桥接脚本，客户端只需要一个 Python 解释器。
3. **嵌入模型下载超时 / 401**
   `HF_ENDPOINT` 走 hf-mirror 解决超时；若日志里出现 `cas-server.xethub.hf.co ... 401`，按 §8.2 加 `HF_HUB_DISABLE_XET=1`。
4. **写入返回 200 但检索为空**
   先确认 `success: true`；再查 8089 嵌入服务是否存活（§8.2 的静默失效模式）；最后核对写入与检索的 `user_id` / `user_ids` 是否同一个用户。

## 9. 总结

这套部署达成三件事：

1. **记忆与算力解耦**：混合存储收敛在 136 常驻，抽取 LLM 走云端 DeepSeek（也可切 240 Jetson 的 `qwen3.8-27b`），`Hy-Memory-30B-A3B` 完全不必部署；
2. **五 Agent 一视图**：agy、codex、zcode、prime-agent 走同一个零依赖 MCP 桥接，pi 走 Skill + CLI，全部统一在 `hxf0223` 用户视图下读写；
3. **可复现**：`.env` + 两个 systemd unit + 一个桥接脚本，新机器十分钟复刻。

2026-10-19 的全量复核修掉了嵌入服务崩溃循环、list 解析、CLI 假成功、user_id 分裂四个问题；遗留事项是 Windows 端与 240 端按 §7.6 补充 `HY_MEMORY_HOST` 后各做一次 §8.1 的验证。
